language১. ANSI Mapping কী?
expand_more

আপনি যখন বাংলায় টাইপ করেন — যেমন "সালাম" — আপনার কম্পিউটার Unicode ব্যবহার করে। কিন্তু পুরনো ফন্টগুলো (যেমন SutonnyMJ) অনেক আগে তৈরি করা হয়েছে — তখন Unicode Encoding ছিল না। তাই ইংরেজি কীবোর্ডের অক্ষরের উপর বাংলা Glyph বসিয়ে ফন্ট তৈরি করা হতো। একে ANSI Encoding বলা হয়।

এই JSON ফাইলটি হল সেই অনুবাদক (Mapping) — এটি ইঞ্জিনকে বলে দেয় প্রতিটি Unicode বর্ণের জন্য কোন ANSI Hex Code ব্যবহার করতে হবে। যেমন:

স (Unicode)   → #$A2 (ANSI Hex Code)
া (Unicode)   → #$79 (ANSI Hex Code)
ল (Unicode)   → #$0153 (ANSI Hex Code)
ম (Unicode)   → #$203A (ANSI Hex Code)

ফলাফল: সালাম (Unicode) → ‡yv (ANSI SutonnyMJ)

মনে রাখুন: এই কনভার্সন শুধু বর্ণ পরিবর্তন নয় — এটি জটিল Cluster, যুক্তাক্ষর, কারচিহ্ন এবং রেফ/ফলার অর্ডারও পরিবর্তন করে। তাই একটি সাধারণ "find-and-replace" দিয়ে এই কাজ হয় না।

account_tree২. JSON ফাইলের গঠন (V3)
expand_more

JSON ফাইলটি ৭টি প্রধান সেকশনে বিভক্ত:

{
  "Constants":             // বর্ণ ও Glyph-এর সংজ্ঞা (৭টি উপ-ক্যাটাগরি)
  "FullFormReplacements":  // পূর্ণ যুক্তাক্ষরের তালিকা
  "PreReplacements":       // Pre-processing প্রতিস্থাপন
  "PostReplacements":      // Post-processing প্রতিস্থাপন (সবার শেষে)
  "VowelRules":            // স্বরবর্ণ-কার Glyph নির্বাচনের নিয়ম
  "ConsonantGroups":       // Unicode ব্যঞ্জনবর্ণের গ্রুপ
  "AnsiGroups":            // ANSI কোডপয়েন্টের গ্রুপ (RaPhalas, Connectors)
}
Constants → ৭টি উপ-ক্যাটাগরি

Numbers (০-৯): অঙ্কের ANSI Mapping

VowelsAndKars: স্বরবর্ণ ও কারচিহ্ন (ি, ী, ু, ূ, ৃ, ে, ৈ, া ইত্যাদি)

Symbols: যতি, প্রতীক ও বিশেষ চিহ্ন (্, ৎ, ং, ঃ, ঁ)

Consonants: ব্যঞ্জনবর্ণ (ক, খ, গ, ঘ...)

FullForms: যুক্তাক্ষরের পূর্ণ Glyph (ক্ক, ক্ট, ক্ত ইত্যাদি)

FirstHalfForms: যুক্তাক্ষরের বাম পাশ (রেফ, ম-এর প্রথম খন্ড ইত্যাদি)

SecondHalfForms: যুক্তাক্ষরের ডান পাশ (য-ফলা, র-ফলা, ল-এর দ্বিতীয় খন্ড ইত্যাদি)

ConsonantGroups → Unicode ব্যঞ্জনবর্ণ গ্রুপ

Unicode বর্ণের গ্রুপিং — VowelRules-এ গ্রুপের নাম রেফারেন্স করা যায়। কনভার্সনের আগে কাজ করে।

"BaseLineRight": ["খ", "গ", "ঘ", "ণ", "থ", "দ", "ধ", "ন", "প", "ব", "ম", "ল", "স", "হ"]
AnsiGroups → ANSI কোডপয়েন্ট গ্রুপ

ANSI কোডপয়েন্টের গ্রুপিং — কনভার্সনের পরে কাজ করে। VowelRules ও FinalTouch উভয় ক্ষেত্রেই ব্যবহার হয়।

"RaPhalas": ["#$C6", "#$C8", "#$C9", "#$CA", "#$CB", "#$CC"]
alt_route৩. কনভার্সন পাইপলাইন ও ফেজ (বিস্তারিত)

Unicode থেকে ANSI-তে রূপান্তর তিনটি ফেজে (Phase) ঘটে। প্রতিটি ফেজের ভিতরে নির্দিষ্ট ক্রমে ধাপগুলো চলে। এই Phased Approach প্রয়োজন কারণ — বাংলার জটিল যুক্তাক্ষর, রেফ, ফলা এবং কারচিহ্নের অর্ডার এমনভাবে জটিল যে একটি একক pass দিয়ে সব কাজ সম্ভব নয়।

fiber_manual_record Phase A: Pre-phase (Raw Unicode Analysis)

এটি কনভার্সনের একদম শুরুতে চলে। যখন টেক্সটটি এখনো সম্পূর্ণ Unicode থাকে। এখানে মূলত উ, ঊ এবং ঋ-কারের বিশেষ রূপগুলো নির্বাচন করা হয় কারণ এই সময়ে Unicode Cluster-এর পূর্ণ রূপটি পাওয়া যায়।

fiber_manual_record Phase B: Main Conversion (The Core)

এখানে মূল রূপান্তর ঘটে। এর ধাপগুলো হলো:
Normalization (DeNormalize) $\rightarrow$ কার ও রেফের স্থান পরিবর্তন $\rightarrow$ পূর্ণ যুক্তবর্ণ প্রতিস্থাপন $\rightarrow$ সাধারণ বর্ণ ও কার প্রতিস্থাপন $\rightarrow$ First/Second Half ফর্ম তৈরি $\rightarrow$ FinalTouch (Santiation)।

fiber_manual_record Phase C: Post-phase (ANSI Polishing)

এটি সবশেষে চলে, যখন টেক্সটটি ইতিমধ্যে ANSI-তে রূপান্তরিত হয়ে গেছে। এখন ইঞ্জিন শুধু দেখে যে কোন ANSI কোডপয়েন্টের পর কোন কার বসবে। এটি মূলত AnsiGroups-এর উপর ভিত্তি করে কাজ করে।

কেন ৩ ফেজ? VowelRules-এ প্রতিটি Mapping-এ "process" ফিল্ড থাকে। "pre" মানে কাঁচা Unicode-তে (Phase A) প্রয়োগ হবে, "post" মানে ANSI-তে রূপান্তরের পর (Phase C) প্রয়োগ হবে, এবং ফাঁকা মানে Phase B (মূল কনভার্সন) তে প্রয়োগ হবে। এই পৃথকীকরণ প্রয়োজন কারণ কিছু কার-কম্বিনেশন শুধু Unicode পর্যায়েই সঠিকভাবে নির্ধারণ করা যায় (যেমন BelowBaseVariant, RuClusters), আবার কিছু শুধু ANSI পর্যায়েই (যেমন RaPhalas)।

কেন এই জটিলতা? কিছু ক্ষেত্রে আমরা জানি বর্ণটি ইউনিকোডে কী ছিল, কিন্তু রূপান্তরের পর সেটি কোন গ্লিফ হয়ে গেল তা জানতে হয়। এজন্য Pre এবং Post ফেজের মাধ্যমে আমরা দুই স্তরেই কন্ট্রোল রাখতে পারি।

Phase A: Pre-phase — কাঁচা Unicode-তে কার নির্বাচন

DeNormalize-এর আগে চলে। এখনো টেক্সট সম্পূর্ণ Unicode — তাই ConsonantGroups (Unicode) দিয়ে ম্যাচ করা যায়।

ApplyRuleForKar(b_Ukar, 'pre');    // উ-কার — process:"pre" Mapping প্রয়োগ
ApplyRuleForKar(b_UUKar, 'pre');   // ঊ-কার
ApplyRuleForKar(b_Rrikar, 'pre');  // ঋ-কার

কেন আলাদা ফেজে? কারণ কিছু Mapping "process": "pre" সেট করা আছে — যেমন BelowBaseVariant, RuClusters। এগুলো মূল কনভার্সনের আগে প্রয়োগ করতে হয়। যেমন, "ট্রু" লিখলে "ট্র" ক্লাস্টারটি Unicode অবস্থায় BelowBaseVariant গ্রুপে ম্যাচ হয়ে সঠিক উ-কার (#$0024 — ছাতা উ-কার) নির্বাচিত হয়। যদি এটি Phase B-তে করা হতো, তাহলে DeNormalize এবং ReArrangeKars-এর পরিবর্তনের পর মূল ক্লাস্টার আর সনাক্ত করা যেত না।

Phase B: Main Conversion — মূল রূপান্তর

Phase B হলো মূল কনভার্সন পাইপলাইন। এখানে ধাপগুলো নির্দিষ্ট ক্রমে চলে:

DeNormalize: Unicode টেক্সটকে সাধারণ রূপে আনে। Z+Nukta থেকে য়, ড়, ঢ় তৈরি করে এবং তিগুণ হসন্ত কমিয়ে দ্বিগুণ করে।

Z + Nukta → Y (য়)
DD + Nukta → RR (ড়)
DDH + Nukta → RRH (ঢ়)
তিগুণ হসন্ত → দ্বিগুণ

ReArrangeKars: I-কার (ি), E-কার (ে), OI-কার (ৈ) Unicode-তে বর্ণের পরে থাকে, কিন্তু ANSI ফন্টে এগুলো বর্ণের আগে বসে। এই ধাপে এদের স্থান পরিবর্তন করে। এছাড়া O-কার ও OU-কার ভেঙে E-কার + AA-কার এবং E-কার + LengthMark-এ পরিণত করে।

ReArrangeReph: রেফ (্র) ANSI-তে বর্ণের পরে বসে। এই ধাপে r + Hasanta প্যাটার্ন সনাক্ত করে রেফকে সঠিক স্থানে (পরবর্তী বর্ণের পরে) নিয়ে যায়। তবে যদি পূর্ববর্তী বর্ণের আগেই Hasanta থাকে (যেমন mrya, krya), তাহলে সেটি রেফ নয়, র-ফলা — তাই এটি স্কিপ করে।

ApplyKarInclusiveFullForms: এই ধাপে সেসব যুক্তাক্ষর প্রক্রিয়া করা হয় যাদের ভেতরে কারচিহ্ন রয়েছে — যেমন ক্রু (ক+র+উ-কার), জ্ঞু (জ+ঞ+উ-কার)। KarInclusiveReplacements তালিকা দীর্ঘতম ম্যাচ আগে বসিয়ে সাজানো থাকে।

ApplyVowelKars: U-কার, UU-কার, এবং RRI-কার এর জন্য সাধারণ পাস। এখানে ApplyRuleForKar ফেজ প্যারামিটার ছাড়া ডাকা হয়, তাই শুধুমাত্র process ফাঁকা Mapping-গুলো প্রয়োগ হয়। এছাড়া বিশেষ ক্লাস্টার যেমন গ+উ-কার→গু, শ+উ-কার→শু, হ+উ-কার→হু সরাসরি প্রতিস্থাপন করা হয়।

ReplaceFullForms: ActiveReplacements তালিকা থেকে সব পূর্ণ যুক্তাক্ষর প্রতিস্থাপন করে। তালিকাটি Key Length Descending ক্রমে সাজানো, তাই দীর্ঘতম ম্যাচ আগে হয়।

ReplaceKarsVowels: E-কার, OI-কার, এবং অন্যান্য সাধারণ কার/স্বরবর্ণ প্রতিস্থাপন করে। E-কার ও OI-কার পরীক্ষা করে — বর্ণের আগে থাকলে "সাধারণ" গ্লিফ, নাহলে "ঝুলন্ত" গ্লিফ ব্যবহার করে।

ConvertRFola_ZFola_Hasanta: য-ফলা (Hasanta+য), র-ফলা (Hasanta+র) এবং হসন্ত গ্লিফে রূপান্তর করে। র-ফলার ক্ষেত্রে পূর্ববর্তী বর্ণের উপর নির্ভর করে বিভিন্ন গ্লিফ নির্বাচন করে (যেমন প/গ/শ+র-ফলা, ভ+র-ফলা, ক/ত+র-ফলা)।

FirstHalfForms → SecondHalfForms → Consonants: যুক্তাক্ষরের বাম ও ডান খণ্ড এবং সাধারণ ব্যঞ্জনবর্ণ প্রতিস্থাপন করে।

FinalTouch: সর্বশেষ ধাপে একাধিক পরিশোধন কাজ হয় — হসন্ত/ZWJ/ZWNJ পরিষ্কার, কার-অর্ডার সুয়াপ, Unicode স্যানিটাইজেশন এবং ApplyGenericGlyphSwaps।

Phase C: Post-phase — ANSI-তে রূপান্তরের পর কার নির্বাচন

Phase C Phase A-এর পরিপূরক। এখনো টেক্সট ANSI-তে রূপান্তরিত হয়ে গেছে — তাই AnsiGroups (ANSI কোডপয়েন্ট) দিয়ে ম্যাচ করা যায়।

ApplyRuleForKar(b_Ukar, 'post');    // উ-কার — process:"post" Mapping প্রয়োগ
ApplyRuleForKar(b_UUKar, 'post');   // ঊ-কার
ApplyRuleForKar(b_Rrikar, 'post');  // ঋ-কার

কেন আলাদা ফেজে? কারণ কিছু Mapping "process": "post" সেট করা আছে — যেমন RaPhalas, BaseLineRight। যেমন, ক্রু লিখলে Phase B-তে র-ফলা ANSI কোডপয়েন্ট #$C6-তে রূপান্তরিত হয়। Phase C-তে ApplyRuleForKar দেখে যে পূর্ববর্তী ক্যারেক্টার #$C6, যা AnsiGroups.RaPhalas-এ আছে — তাই A_UKar2 (ঝুলন্ত উ-কার) নির্বাচিত হয়।

ফেজ ভিত্তিক প্রক্রিয়া — কেন প্রয়োজন?

বাংলা ভাষার জটিলতা কারণে এই Phased Approach অপরিহার্য:

  1. Unicode বনাম ANSI পরিচিতি: কিছু ক্লাস্টার (যেমন ট্র, ড্র) শুধু Unicode অবস্থায় চেনা যায় (ConsonantGroups), আবার কিছু (যেমন র-ফলা #$C6) শুধু ANSI অবস্থায় (AnsiGroups)।
  2. অর্ডার সংবেদনশীলতা: DeNormalize ও ReArrangeKars টেক্সটের অর্ডার পরিবর্তন করে। Phase A এই পরিবর্তনের আগে কাজ করে, Phase C পরে।
  3. ফলব্যাক ব্যবস্থাপনা: যদি Phase A কোনো Mapping-এ ম্যাচ না পায়, তাহলে ApplyRuleForKar Phase B-তে ডিফল্ট মান ব্যবহার করে। Phase C তখন সেই ডিফল্টের উপর পুনরায় ম্যাচ চেষ্টা করে।
rule৪. VowelRules: স্বরবর্ণ-কার Glyph নির্বাচন (বিস্তারিত)

Mapping-Level ফিল্ডসমূহ

ফিল্ড মান ব্যাখ্যা
process "pre" / "post" / (ফাঁকা) কোন ফেজে এই Mapping প্রয়োগ হবে। "pre" = Phase A, "post" = Phase C, ফাঁকা = Phase B (মূল)
matchMode 0 / 1 ০ = পূর্ণ Cluster দীর্ঘতম Match (ডিফল্ট)। ১ = কারের ঠিক আগের একটি বর্ণ মাত্র
toggle "backspace" / (ফাঁকা) এই Mapping-এ Toggle সক্রিয় করবে কিনা। "backspace" = ব্যাকস্পেসে State ফ্লিপ

MatchMode: ক্লাস্টার বনাম ক্যারেক্টার ম্যাচ

Mode 0

Full Cluster Longest Match: কারের আগের পুরো অংশটি চেক করে। যদি 'ট্র' একটি গ্রুপে থাকে, তবে সেটি দীর্ঘতম ম্যাচ হিসেবে প্রাধান্য পাবে।

Mode 1

Last Char Only: পুরো ক্লাস্টার না দেখে শুধুমাত্র শেষের অক্ষর বা বর্ণটিি বর্ণটি চেক করে।

FindBestClusterMatch ফাংশন সব Mapping স্ক্যান করে এবং দীর্ঘতম Match বেছে নেয়। MatchMode-এর উপর নির্ভর করে ম্যাচিংয়ের পদ্ধতি ভিন্ন হয়:

MatchMode ০ (পূর্ণ Cluster Match — ডিফল্ট):

কারের অবস্থান থেকে পিছনে Scan করে। প্রথমে ConsonantGroupMap ও AnsiGroupMap-এর তালিকায় দীর্ঘতম Match খুঁজে। MatchGroupLength ফাংশন Block-based Matching ব্যবহার করে — character-by-character নয়, বরং পুরো গ্রুপ এন্ট্রিকে একটি Block হিসেবে পূর্ববর্তী টেক্সটের সাথে তুলনা করে।

উদাহরণ: "ট্রু" — কারের আগে "ট্র"
→ RuClusters-এ "ট্র" আছে (দৈর্ঘ্য ২)
→ MatchLen = 2 → value = #$0024 (ছাতা উ-কার)

MatchMode ১ (শুধু শেষ বর্ণ):

শুধু কারের ঠিক আগের একটি বর্ণের সাথে Direct Char Match করে। পুরো Cluster দেখে না।

উদাহরণ: "রু" — কারের আগে "র" (#$09B0)
→ Direct Match: consonants = "#$09B0" = "র"
→ value = A_UKar4 (রেফ-স্টাইল উ-কার)

অগ্রাধিকার (Priority):

সব Mapping-এর মধ্যে যেটি দীর্ঘতম MatchLen দেয়, সেটি বেছে নেওয়া হয়। একই MatchLen হলে প্রথমে পাওয়া Mapping-টি ব্যবহার হয়।

Best-Match অ্যালগরিদম — কিভাবে কাজ করে

FindBestClusterMatch ফাংশনটি নিম্নরূপ কাজ করে:

  1. কারের ঠিক আগের ক্যারেক্টার সনাক্ত করে (Z-fola--aware: যদি আগে Hasanta+য থাকে, তাহলে তা বাদ দিয়ে মূল বর্ণ খুঁজে)
  2. সব Mapping-এর উপর Loop চালায়
  3. MatchMode ০ হলে MatchGroupLength দিয়ে ConsonantGroupMap ও AnsiGroupMap-এ খুঁজে
  4. MatchMode ১ হলে শুধু Direct Char Match করে
  5. সবচেয়ে বড় MatchLen এর Mapping সংরক্ষণ করে
  6. ফলাফল হিসেবে MatchedCluster, BestMapping, BestMatchLen, ContextEnd, IsZfola ফেরত দেয়

Toggle মেকানিজম (V3 — Mapping-Level)

V3-তে toggle ফিল্ড প্রতিটি Mapping-এর ভিতরে থাকে (Rule-level নয়)। এটি নির্ধারণ করে সেই নির্দিষ্ট Mapping-এর alt মান কখন সক্রিয় হবে।

Toggle State Storage:

fToggleStates Dictionary Key: MatchedCluster + '_' + OccurrenceIndex + '_' + KarChar
যেমন: "গ্র_1_#$09C1" = "গ্র" Cluster-এ ১ম উ-কারের Toggle State

Backspace Detection: আগের ইনপুট fLastUniText এবং বর্তমান ইনপুট তুলনা করে। যদি বর্তমান = আগের − কার, তাহলে সেই নির্দিষ্ট Cluster-এর OccurrenceIndex খুঁজে Toggle State ফ্লিপ করে।

Best-Match Toggle Resolution: FindMappingToggle ফাংশন সব Mapping স্ক্যান করে, দীর্ঘতম Match-এর Mapping-এর ToggleOnBackspace সেটিং ফেরত দেয়। এটি নিশ্চিত করে যে শুধু সেই Mapping-টি Toggle-এর প্রভাবে পরিবর্তিত হয় যেটি সত্যিই Match হয়েছে।

Toggle-এর ফলাফল:

Toggle OFF (Default): value = A_UKar4 (#$26 — রেফ-স্টাইল)
Toggle ON (Backspace): alt = A_UKar2 (#$24 — ঝুলন্ত)
ব্যাকস্পেস চাপলে: উভয়ের মধ্যে টগল হয়

Matching Priority — কোন ক্রমে খোঁজা হয়

FindBestClusterMatch নিম্নলিখিত ক্রমে ম্যাচ খুঁজে:

  1. Direct Char Match: Mapping-এর consonants কী সরাসরি ক্যারেক্টারের সাথে মিলে (যেমন "#$09B0" = "র")
  2. ConsonantGroups Match: ConsonantGroupMap-এ গ্রুপের নাম দিয়ে খোঁজা হয় (যেমন "RuClusters", "BelowBaseVariant")
  3. AnsiGroups Match: AnsiGroupMap-এ গ্রুপের নাম দিয়ে খোঁজা হয় (যেমন "RaPhalas") — শুধু Phase C তে
  4. Default: কোনো Mapping না মিললে default মান ব্যবহার হয়

গুরুত্বপূর্ণ: default মানের কোনো alt নেই, তাই Toggle কখনোই default-কে প্রভাবিত করে না। Mapping-এ alt ফাঁকা রাখলে ঐ Mapping-টি Toggle-এর প্রভাবে অপরিবর্তিত থাকে।

বাস্তব উদাহরণ

রু (র + উ-কার): পূর্ববর্তী বর্ণ #$09B0 (র) — Direct Match, matchMode=1, process="pre" → value = A_UKar4 (রেফ-স্টাইল)। toggle="backspace" থাকায় alt = A_UKar2 (ঝুলন্ত) এ ফ্লিপ করে।

ট্রু (ট + র + উ-কার): "ট্র" BelowBaseVariant গ্রুপে আছে, matchMode=০ → value = #$0024 (ছাতা উ-কার)।

ক্রু (ক + র + উ-কার): ANSI-তে রূপান্তরের পর র (#$C6) — RaPhalas (AnsiGroups), process="post" → value = A_UKar2 (ঝুলন্ত)।

গু (গ + উ-কার): "গ" BaseLineRight গ্রুপে, matchMode=১ → A_UKar1 (সাধারণ)।

৩টি গ্রুপের বিস্তারিত ব্যাখ্যা

ConsonantGroups (Unicode)

এটি কনভার্সনের আগে কাজ করে। যখন ইঞ্জিন জানে বর্ণটি ইউনিকোডে কী, তখন এই গ্রুপ ব্যবহার করে।

উদাহরণ: "BelowBaseVariant": ["ট্র", "ড্র"]

AnsiGroups (ANSI)

এটি কনভার্সনের পরে কাজ করে। যখন বর্ণটি ইতিমধ্যে ANSI হেক্স কোডে পরিণত হয়েছে, তখন এই গ্রুপ ব্যবহৃত হয়।

উদাহরণ: "RaPhalas": ["#$C6", "#$C8"]

এই দ্বৈত পদ্ধতির ফলে আমরা অনেক জটিল গ্লিফ হ্যান্ডেল করতে পারি। যেমন: 'ক' এর পরে 'র-ফলা' বসলে সেটি ইউনিকোড থেকে ANSI-তে রূপান্তর হয়ে #$C6 হয়ে যায়। এখন যদি তার পরে 'উ-কার' আসে, তবে ইঞ্জিন AnsiGroups.RaPhalas দেখে বুঝতে পারে যে এখানে বিশেষ গ্লিফ বসাতে হবে।

BelowBaseVariant: এমন যুক্তবর্ণ যাদের নিচে র-ফলা ঝুলে না থেকে সোজা বা ছাতার মতো বসে। যেমন "ট্র", "ড্র", "ঢ্র" — এদের নিচে উ-কার দিলে বিশেষ Glyph (#$0024 — ছাতা উ-কার) ব্যবহার করতে হয়। MatchMode ০ ব্যবহার করে পুরো Cluster Match করে।

RuClusters: র-ফলা যুক্ত Cluster (গ্র, ত্র, দ্র, ন্র, প্র, ব্র, ভ্র, ম্র, শ্র, ষ্র, স্র, হ্র)। এদের নিচে উ-কার দিলে র-ফলার সাথে সংঘর্ষ এড়াতে বিশেষ উ-কার (A_UKar4 — রেফ-স্টাইল) ব্যবহার করা হয়। Toggle সাপোর্টেড — ব্যাকস্পেসে A_UKar1 (সাধারণ) এ ফ্লিপ করা যায়। MatchMode ০ ব্যবহার করে।

BaseLineRight: ডানপাশে খাড়া Stem যুক্ত বর্ণ ও যুক্তবর্ণ। এদের নিচে সাধারণ ঝুলন্ত উ-কার (A_UKar1) বসে। র-ফলাসহ Cluster এখানে লাগে না — AnsiGroups.RaPhalas স্বয়ংক্রিয়ভাবে হ্যান্ডল করে। MatchMode ১ ব্যবহার করে — শুধু শেষ বর্ণ চেক করে। Phase C (Post-phase) তে কাজ করে।

বাকি থাকা Unicode Hasanta, ZWJ (Zero Width Joiner), এবং ZWNJ (Zero Width Non-Joiner) Glyph-গুলো সরিয়ে ANSI Hasanta-তে রূপান্তর করে।

২. কার-অর্ডার সুয়াপ

ANSI ফন্টে কিছু কম্বিনেশনে কারচিহ্ন বর্ণের আগে বসে (যেমন র-ফলা + উ-কার), কিন্তু সঠিক অর্ডার হলো কার + র-ফলা। FinalTouch এই সমস্যা সমাধান করে:

ZFola + UKar → UKar + ZFola
RFola + UKar → UKar + RFola
Reph + UKar → UKar + Reph
Reph + UUKar → UUKar + Reph

৩. পোস্ট-প্রসেসিং কারেকশন

নির্দিষ্ট বর্ণ + কার কম্বিনেশনের জন্য বিশেষ সংশোধন:

ট + উ-কার১ → ট + উ-কার২ (ঝুলন্ত)
ঊ-কার১ + ড় → ঊ-কার২ + ড়
ঊ-কার১ + র → ঊ-কার২ + র

৪. Unicode স্যানিটাইজেশন

আউটপুট থেকে সব Unicode Bengali ক্যারেক্টার (U+0980–U+09FF) এবং অদৃশ্য ক্যারেক্টার (ZWJ, ZWNJ) সরিয়ে দেয়। এটি নিশ্চিত করে যে চূড়ান্ত আউটপুট শুধুমাত্র ANSI কোডপয়েন্ট ধারণ করে।

৫. ApplyGenericGlyphSwaps — স্বয়ংক্রিয় অর্ডার সংশোধন

এটি FinalTouch-এর সবচেয়ে শক্তিশালী ফিচার। এটি সম্পূর্ণভাবে স্বয়ংক্রিয় — ব্যবহারকারীকে প্রতিটি কম্বিনেশনের জন্য আলাদা নিয়ম লিখতে হয় না।

  1. Modifier Collection: AnsiGroups থেকে সব Modifier Glyph লোড করে (RaPhalas + Connectors)। ফলব্যাক হিসেবে RFola, ZFola, Reph, RR, R, RRH ব্যবহার করে।
  2. Kar Collection: সব কার Glyph লোড করে — A_UKar1-4, A_UUKar1-3, A_RRIKar1-2।
  3. Nested Loop: প্রতিটি Modifier-এর জন্য প্রতিটি কার-এর সাথে ReplaceStr চালায়।
  4. Swap: যদি Modifier + Kar প্যাটার্ন পাওয়া যায়, তাহলে Kar + Modifier-এ পরিবর্তন করে।
উদাহরণ: র-ফলা(#$C6) + উ-কার(#$25)
